Website interface research

Look closer at the web.

Exploring how automation and AI can help identify dark patterns in website interfaces.

DarkSense AI explores how AI can help identify potentially deceptive design patterns on e-commerce websites. I worked on website collection, a BERT-based text-classification experiment, and an EfficientNet preprocessing and inference pipeline. The project combines practical automation with an important caveat: model predictions are signals to review, not proof of intent.

Project focus

Interfaces can influence decisions.

The project examines website UI and text for signals that may warrant closer review. A detected signal needs context; it is not, by itself, proof of intent.

  • Python scraping and Selenium browser automation
  • BERT text classification with Hugging Face Transformers
  • EfficientNet visual-analysis exploration with PyTorch
01 / About

Make the interface easier to question.

Dark patterns are interface or wording choices that can manipulate users into decisions they might not otherwise make. This project focuses on e-commerce websites and explores how website text, visual information and heuristic indicators can surface potentially deceptive patterns for closer inspection.

I chose this problem because it connects practical web automation with applied AI: manual inspection is repetitive, while text alone may miss important visual context. The goal is to investigate a useful detection approach without treating a model prediction as proof of deliberate deception.

02 / Approach

Collect evidence first. Interpret it carefully.

The work spans collection, dataset preparation, text classification and visual analysis. These components have different levels of verification; the complete pipeline is not presented as a deployed service.

STEP 01

Collect

I explored Python scraping, an initial HTMLParser text-extraction approach, and Selenium-based crawling to inspect e-commerce pages, collect page text and screenshots, and handle dynamic-page failures. Project notes also record a crawler CSV with about 1,800 URLs, collection work involving more than 15,000 URLs and 10,000 UI screenshots, and research using a list of roughly 1,048,000 ranked domains. These are distinct collection/research figures, not labeled training-example counts.

STEP 02

Prepare and analyze

I prepared a binary text-classification dataset: 1 for Dark Pattern and 0 for Not Dark Pattern. Project notes record about 3,460 cleaned records and an 80:20 train/test split (about 692 test samples). I trained and ran inference with bert-base-uncased using Hugging Face Transformers, and explored EfficientNet preprocessing and inference with PyTorch for visual analysis.

STEP 03

Review

Consider urgency wording, scarcity claims, countdown timers, misleading discounts and pressure-oriented language as possible signals. False positives, data quality and the context of each interface matter; a signal alone does not establish intent.

03 / Implementation

From website evidence to model experiments.

A closer look at the work: website collection, the BERT experiment, and visual-analysis exploration.

01COLLECTION

Browser-based inspection

Python and Selenium were used in the collection workflow discussed previously. The work included URL crawling, extracting page text, taking UI screenshots, and handling dynamic pages and crawl failures. HTMLParser was part of an earlier text-extraction approach.

02NLP EXPERIMENT

BERT text classification

The experiment used bert-base-uncased with Hugging Face Transformers and the Trainer workflow. I prepared labeled data, tokenized text, trained and saved the model, implemented inference for new text, and examined precision, recall, F1 score, a confusion matrix, false positives and false negatives. Project notes record approximately 3,460 cleaned records and 97.4% test accuracy for this BERT experiment; this is a previously recorded result, not a newly reproduced measurement, and it does not represent a fully integrated website-level detector.

03VISUAL EXPLORATION

EfficientNet pipeline

I also worked on an EfficientNet preprocessing and inference pipeline using PyTorch to explore visual information from website interfaces alongside extracted text. The broader approach considers heuristic signals such as urgency wording, scarcity claims, countdown timers, misleading discounts and pressure-oriented language. A final visual-model accuracy and a verified end-to-end result combining text and visual models are not established in the available project notes.

Engineering considerations

Integration discussions covered API integration, multimodal fusion and end-to-end testing. Practical crawler concerns included explicit waits, exception handling, retries, missing-element checks and per-URL logging. The key lesson is that model accuracy and system reliability are different: collection failures, data quality, false positives and the interaction between components all affect a reliable result. The exact final status of every integration component is not established.

Collection reliability

Plan for the pages that don't behave.

Real websites are inconsistent. The cases below are important safeguards for a dependable crawler; they should be read as handling guidance, not as proof that every safeguard is already implemented in this project.

01URL VALIDATION

Malformed, duplicate or unsupported URLs

Validate and normalize URLs before visiting them; reject empty or malformed entries and unsupported schemes. Track canonicalized URLs to avoid duplicate work, and keep the original URL alongside the normalized one for traceability. Record skipped entries with a reason rather than silently dropping them.

02NETWORK FAILURES

Timeouts, blocked requests and transient errors

Use bounded page-load and element-wait timeouts. Retry only transient failures with a small retry limit and backoff; do not loop forever on access-denied pages, persistent 4xx responses or repeated browser crashes. Log the URL, stage, error category and attempt count so failed visits can be investigated separately.

03DYNAMIC CONTENT

JavaScript rendering, lazy loading and pop-ups

Use Selenium when content is rendered after page load. Wait for a meaningful element or a bounded readiness condition instead of relying only on fixed sleeps. Treat cookie banners, overlays, lazy-loaded sections and navigation changes as possible sources of missing or obscured content; capture what was observed and note when extraction may be incomplete.

04MISSING DATA

Empty text, missing elements and failed screenshots

Check that extracted text is non-empty and screenshots were actually written before marking a visit successful. Keep text and screenshot status separately, because one may succeed while the other fails. Store explicit statuses such as success, partial, empty or failed rather than substituting invented content.

05DATA QUALITY

Boilerplate, duplicates and inconsistent labels

Remove obvious repeated records and irrelevant page chrome only with a documented, repeatable rule. Preserve useful context such as the page URL and capture time. Validate the binary label mapping (1 = Dark Pattern, 0 = Not Dark Pattern), inspect conflicting or uncertain examples, and avoid turning missing evidence into a negative label automatically.

06CRAWL SAFETY

Rate limits, resource use and resumability

Set sensible concurrency and request pacing, respect site access rules, and limit page depth, navigation loops and per-site work. Save progress incrementally so a crash does not discard an entire run; make reruns idempotent where possible and record why a URL was skipped or retried. Avoid collecting credentials, personal data or unrelated sensitive content.

07REPRODUCIBILITY

Trace each record to its collection outcome

For each attempt, keep a structured record of URL, timestamp, extraction status, error category, text length, screenshot path/status and crawler version or configuration. Review failure rates and a sample of collected pages before model training. This makes it easier to distinguish a genuine absence of a signal from a collection failure.

These are recommended robustness practices for the collection workflow. The available project notes establish that dynamic pages, crawl failures and data-quality challenges were relevant, but do not verify that every control listed above is present in the current crawler code.

Project takeaways

What the work taught me.

DarkSense AI connected several practical engineering and machine-learning concerns.

Data collection
Collecting website information and handling real-world crawling difficulties.
Machine learning
Preparing labeled datasets and training, saving and running inference with a transformer-based classifier.
Evaluation
Looking beyond accuracy at precision, recall, F1, false positives and false negatives.
System thinking
Exploring visual analysis alongside NLP and understanding the challenges of integrating components reliably.

A strong text-classification result does not by itself establish that a complete website detector works reliably. Data quality, crawler behavior and end-to-end integration also matter.
